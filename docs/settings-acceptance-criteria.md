# League Administration / Settings acceptance criteria

These criteria cover the seven findings from the October 6 test report. A saved-setting test is not evidence of downstream enforcement. Existing successful role, persistence and retry checks must continue passing.

1. **Transactions load safety (P1).** Until the selected league's configuration loads successfully, no transaction or draft-rule fields may be saved. A failed read displays an error and an explicit retry. Retry loads persisted settings; it never replaces them with defaults. Failed writes preserve edits. Switching leagues cancels stale loads and cannot save a previous league's configuration.
2. **Concurrent scoring edits (P1).** Each loaded configuration carries a revision. Saving requires that revision to match the stored configuration, checked atomically. A stale save returns 409, changes no scoring values, displays a conflict, and preserves draft edits. An explicit reload replaces the draft with the saved values; the commissioner can reapply and save an edit. Legacy API clients remain compatible, and their successful saves advance the revision so browser clients detect those changes too. Simultaneous saves cannot both overwrite the same revision.
3. **Player Pool persistence (P2).** All exposed player-pool fields are controlled values loaded from the selected league. Explicit Save persists NHL/team/conference selections, pool lock, minors/unsigned switches and the duplicate-player mode. Successful reload reflects the saved values. Failed loads cannot save defaults; failed saves preserve edits. Values are isolated between leagues and restricted to commissioners/co-commissioners. **Runtime enforcement is a separate acceptance gate:** excluded players cannot be acquired through roster, waiver or draft paths, and duplicate-player modes must have a consistent ownership contract across trades/scoring/history. Persistence alone does not close that gate.
4. **Prospect eligibility (P2).** League updates validate and persist age 16–30 and career games 0–500; GET returns both fields and browser reload retains them. Invalid requests reject the whole update. Explicit zero games is preserved and used by prospect classification; omitted values retain the established defaults. Prospect claim prevention must use these saved thresholds.
5. **Co-commissioner access (P2).** An explicit co_commissioners membership grants the Settings page and scoring configuration write access. Managers, outsiders, anonymous and expired sessions remain denied. Authority is rechecked by the API at save time; revoked authority cannot write from an already-open page. Other administration endpoints retain their own existing role contracts; this change does not assert universal access to every destructive operation.
6. **Claim limits (P2).** New season limits must be 0–600 and weekly limits 0–100, or null for unlimited. Zero retains the existing API meaning of no allowed claims. All three fields in each bucket follow these bounds. Invalid writes produce a client error before mutation; no partial settings or audit write occurs. The browser clamps its numeric controls within the displayed range. Historical configurations remain readable so invalid old values can be corrected safely.
7. **Blank scoring inputs (P2).** Clearing an enabled weight leaves it blank, and Save displays validation without an API write. An explicit 0 is valid and persists as 0; supported negative and decimal weights continue working. Disabled categories may omit their weights. Validation does not discard other edits.

Verification requires fresh isolated fixture data, no automatic retries, preserved failed-run evidence, and testing the rendered UI as well as persisted API/database values. Core gap cases run in Chromium, Firefox and WebKit, with mobile web tab navigation. Real-device/Expo coverage and exact remote-v8/deployment attribution remain separate gates.
