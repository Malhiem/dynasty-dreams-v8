# Immediate league exit

An authenticated member may POST `/api/leagues/{league_id}/leave` with `{ "expected_user_id": "<current authenticated user ID>" }` at any season/setup stage. No successor acceptance, commissioner approval, roster/cap state or payment-policy condition blocks exit. The caller can remove only their own membership. The expected-user guard binds both attempts to the original account and rejects a changed account with 409 before lookup or mutation. Read-only impersonation remains blocked by the existing global authentication guard.

Exit atomically removes commissioner/owner/admin/co-commissioner roles and all ownership/co-ownership inside that league. Owned franchises become vacant; rosters, lineups, scores, league history and existing franchise obligations are retained. Other leagues and other users' roles are unchanged. The last commissioner may leave: the commissioner ID becomes an empty string, the display name becomes Vacant, and `commissioner_vacant=true`. No other user is automatically promoted. Existing administrators retain their authority. Successor assignment is separate and never a condition of leaving.

The transaction stores a caller-scoped exit receipt and one membership audit event. Retrying after a lost response returns the existing receipt without duplicate events. Rejoining through a supported membership flow establishes a new membership that may be left again. This multi-document operation requires the application's transactional MongoDB deployment. Infrastructure failure must be reported as an unconfirmed operation, never a business-rule prohibition on leaving.

After commit, the current Socket.IO server removes the departed user from that league and its draft rooms and informs their sessions, preserving personal and other-league subscriptions. API authorization immediately uses the changed membership. Production multi-worker socket-manager propagation remains part of deployment verification.

The dashboard League options menu offers Leave league separately from reversible Hide. The dialog explains vacancy and invitation requirements, permits cancellation and does not ask for another user's approval. Confirmation is guarded against repeat submission; one retry can reconcile an unknown response using the idempotent endpoint. Active context and private read caches are invalidated and the dashboard reloads. Other tabs refresh through the membership/storage events.
